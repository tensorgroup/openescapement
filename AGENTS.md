# OpenEscapement

Deterministic governance for AI usage: the `esc` CLI syncs versioned, signed rule packs into the instruction files coding agents natively read (CLAUDE.md, AGENTS.md, GEMINI.md, skills dirs, MCP config). v0.1 of the CLI is implemented; the registry, dashboard, MCP server, and telemetry pillars are future work.

These are the canonical instructions for any coding agent working in this repo. `CLAUDE.md` imports this file; edit here, not there.

## Build, test, lint

- Go 1.24, module `github.com/tensorgroup/openescapement`, binary `esc` (`cmd/esc`)
- `go test ./...` — integration tests build real temp git repos, no mocks. `ESC_CACHE_DIR` overrides the pack cache; tests rely on it.
- `go vet ./...` and `gofmt -w .` before claiming work done

## Gotchas and invariants

- **Single external dependency policy:** `gopkg.in/yaml.v3` only. Everything else is stdlib; system `git` via `os/exec`. This is a security posture (this tool writes instructions agents execute), not a preference. Adding a dependency needs explicit justification.
  - Exception (display-only): `github.com/yuin/goldmark` renders markdown for the admin portal's browser views. Scope is strictly display: it never runs in the renderer or engine that writes instruction files. It carries zero transitive dependencies (empty require graph), is pinned by `go.sum`, and runs with raw HTML disabled (no `html.WithUnsafe`). Any wider use, or any second display dependency, needs the same explicit justification.
- Sentinel errors in `internal/esc` map to exit codes: 0 ok, 1 drift/constraint, 2 usage, 3 integrity/signature, 4 other. New failure modes go through them.
  - Containment refusals are the deliberate exception: a symlink where escapement is about to write, or a lockfile entry escaping its directory, returns a plain error (exit 4), never `ErrConstraint`. Exit 1 is what a CI gate reads as routine and self-healing, and no amount of syncing resolves a containment failure. Exit 3 belongs to pack integrity (moved tag, tampered fetch, bad signature) and would name the wrong incident for something that is a property of the local checkout.
- Renderer invariants, all golden-testable: bytes outside a managed block are never modified; nothing is written after a verification or constraint failure; all writes are atomic; renderer output is deterministic.
- **Byte preservation is not sufficient.** Any code that inserts into or reconciles a user-owned file must preserve the file's structural meaning, not just its bytes. Three bugs in one cycle satisfied "bytes outside the managed block are never modified" exactly while breaking what the file meant: `placeEnd` appended a marker to a file with no trailing newline, so sync spliced a managed block into the middle of the user's last line; `placeAbove` wrote at byte 0 above a `---` fence, so YAML frontmatter stopped being frontmatter and rendered as a setext heading plus a rule; the plan-time dir walk and `pack.DirHash` filtered `.git` and symlinks differently, so a pristine skill directory reported permanently altered. When touching any write or reconcile path, ask which file shapes (no trailing newline, CRLF, frontmatter, empty file) make a byte-correct write structurally wrong, and either handle the shape or fail closed. The write-path × file-shape matrix in the tests is the guard. Extend it with every new write path.
- **Two orthogonal axes per artifact:** `managed` (`in-sync`, `altered`, `stale`, `missing`, `orphan`, `occupied`) describes content escapement owns. `local` (`none`, `amended`) describes content it does not. Never collapse them: a team can both append its own rules and carry an inadvertent edit inside a managed block, and one enum would force dropping one of those facts. A local amendment alone is never drift and never changes an exit code.
- **Local amendments are preserved for every artifact kind.** Bytes outside a managed block, non-owned `.mcp.json` server entries, and files added to a skill directory all survive every sync. Skill directories carry a per-file manifest in the lockfile (`LockArtifact.Files`), which is what distinguishes a file the team added from one the pack dropped. Retiring a skill directory is not consent to delete what is in it: the removal pass takes only manifest paths, and declines the retirement outright (skip, exit 0, lock entry carried forward) if the directory still holds team-added files or if the manifest's dir hash shows a pack-provided file was edited. `esc status` reports a retired skill directory as an `orphan` finding before sync is ever asked to delete it, the same way it already does for an orphaned managed block, so a retirement sync declines stays visible to `esc status --check` instead of passing the gate at exit 0 forever. Lockfile `Files` entries are untrusted input: contain them and refuse symlinks over the whole manifest before anything reads it, since hashing is a read.
  - **Ownership of a skill directory is the parent path, not a name prefix.** Both the retirement pass and the orphan pass use `ownedSkillPath` (exactly one element below `.claude/skills`), not the old `esc-` prefix: a name-overridden skill (`pack.SkillEntry.Name`) has no prefix, so prefix-based ownership would make its retirement refuse forever. A hostile lockfile is confined by `ownedSkillPath` plus manifest-only deletion, with containment and symlink refusal already run before any of it reads the disk — not by the recorded-hash gate: the lockfile is attacker-controlled and the hash is deterministic, so a hostile entry can simply carry the correct hash. That gate's real job is catching a team member's edit to a pack-provided file so retirement never deletes it silently.
- **`esc sync` skips hand-edited managed regions.** It warns on stderr and exits 0. The lockfile entry for a skipped artifact is left unchanged, so the alteration keeps reporting until someone resolves it: writing the new hash would make it silently vanish from the next `esc status`. `esc sync --force` overwrites the managed region and converges; it never touches a local amendment. Exit 0 from `esc sync` no longer asserts the repo matches policy: it asserts everything escapement was willing to apply was applied. Compliance gating belongs on `esc status --check` (bare `esc status` exits 0 on ordinary drift and always has).
- **Sync never adopts a directory it did not create, with one carve-out.** A `KindDir` artifact with no prior lock entry whose target path already exists is skipped (`SkipUnmanagedDirAtTarget`, exit 0) and reported by status as `occupied` (gates `--check`). `--force` does not override this case: force is consent to overwrite escapement's own content, and this content never was; adoption requires moving the directory aside. The one exception is when the pre-existing directory's content hash exactly equals the artifact escapement would have written: there is nothing to destroy, so sync adopts it — writes the lock entry, writes nothing to disk, prints a stderr notice — which is also what lets a sync interrupted between a dir write and the final lock save converge on retry instead of dead-ending on "occupied" forever.
- **The skip-on-hand-edit gate requires a prior lockfile entry.** A user who deletes `.escapement/escapement.lock` makes every artifact look never-synced, so the very next `esc sync` overwrites every hand-edit with no warning, because there is no prior hash to compare against. Do not delete the lockfile to "reset" a repo.
- **New managed blocks are inserted at the top of a file**, after YAML frontmatter and a leading H1. Existing blocks are replaced in place and never move. `<!-- escapement:block -->` remains the explicit override for placement.
- **`esc init` detects existing instruction files** (`internal/cli/initscan.go`) and, on a TTY, asks once whether to write the placeholder marker and once where it should go, applying that one answer to every eligible file (`internal/cli/initoffer.go`). The gate defaults to no; declining, an empty answer, EOF, unrecognized input, `--yes`, and any non-interactive run all write nothing. It never writes rendered policy, only the marker. The undo rule stated exactly: init never writes over a file with uncommitted changes, because git is what would restore it; where there is no git repository at all there is no undo, so the prompt says so and the write still requires an explicit yes. Init writes to a detected file only when a human answers yes on a TTY.
- **`internal/publisher.Publish` is always non-fatal.** It runs after `esc sync`/`esc status` have already written the lockfile and printed their own output, and nothing it does may retroactively change that command's exit code or suppress what was already printed: a telemetry outage must never break a policy sync. A transport failure (connection refused, timeout, a non-2xx status) is handled by queuing to the local outbox and printing one line to stderr, never by propagating an error to the caller. A missing `ESC_PORTAL_TOKEN` is different: that's a configuration state, not an outage, so `Publish` prints one stderr warning and returns without queuing anything.
- **The redaction walk test enforces the privacy posture.** The walk test in `internal/publisher` (`redact.go`) is the enforcement point, not a detail worth trading away for a simpler contract. Below `reporting.amendments: content`, `Redact` empties `Finding.Amendment.Content`, `Finding.Alteration.Diff`, `Finding.Detail`, and `Skipped.Reason`: all four are human prose, and `Detail`/`Reason` are populated in places directly from `err.Error()`, an unbounded channel for local error text. Everything else, including `Subject`, `Amendment.Items`, counts, hashes, `managed`/`local` states, pack pins, and the cross-level `duplicate` finding (a skill name plus a same/differs bool, nothing else), is metrics-grade by design and must keep surviving below `content`; do not fold any of it into this redaction pass. The test walks the marshalled payload rather than asserting on struct fields, so a new content-shaped field added anywhere in `engine.Report` or `publisher.Envelope` fails it by default instead of leaking silently.
- **`esc pack add-skill`, `update-skill`, and `outdated` are author commands.** They run in the pack repo and vendor an external skill with provenance rather than reference it at sync time: an org's signature must cover the exact bytes an agent will execute. Provenance (source URL, subdir, requested ref, resolved commit, dir hash) lives in `sources.yaml` at the pack root, outside the skill directories, so a vendored copy stays byte-identical to upstream and no walk has to filter a provenance file out of it. `skills:` entries in `pack.yaml` are a union (`examples/packs/acme-org/pack.yaml` uses the legacy branch): a plain string keeps the `esc-<pack>-<dir>` prefix; an object `{path, name}` sets the on-disk name, which is what lets a vendored suite (e.g. superpowers) keep its upstream names instead of being renamed out from under its own internal cross-references. `update-skill`'s divergence gate mirrors sync's hand-edit rule: a vendored copy edited after the fact is skipped, not silently overwritten, unless `--force`. `outdated --check` exits 1 when anything is behind, for CI on the pack repo; a network failure stays exit 4, since a dead remote must not read as up to date. The MCP-float warning (an unpinned `@latest` or version-less npx server) is printed by these `esc pack` commands only, never by `sync`/`status`: a consumer cannot fix an author's floating pin, so warning them every sync is noise aimed at the wrong person.
- **The outbox is a bounded local queue.** `.escapement/outbox.jsonl` (gitignored) is capped at `OutboxCap` (200 entries) and `OutboxMaxAge` (14 days); eviction drops the oldest entries first and every drop is reported on stderr, since a silently truncating queue would read as healthy telemetry while losing data. `FlushOutbox` classifies a permanent HTTP rejection (400/404/405/413/415/422, `internal/publisher/publisher.go`'s `permanentStatus`) as a drop rather than a retry, so one poisoned payload (e.g. oversized content past the portal's cap) cannot head-of-line-block every later entry queued behind it on the same endpoint; every other status (network errors, 5xx, 429, 401, 403) stays transient and retains the entry for the next flush.

## Working conventions

- Spec-driven: substantive product or architecture decisions get captured in the spec or a design doc, not left in conversation.
- Open-core: the pack format, renderer, CLI, and base MCP server must stand alone without the SaaS control plane.
- YAGNI ruthlessly. Lightweight over complete, privacy-respecting by default (no prompt-content collection), self-hostable, boring and fast.
