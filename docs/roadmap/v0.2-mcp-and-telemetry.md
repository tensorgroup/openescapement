# v0.2 — MCP Server, Telemetry & Dashboards (Brainstorm / Design)

**Status:** Brainstorm. Not yet a committed plan — decisions marked ❓ are open.
**Depends on:** v0.1 CLI (shipped). **Parent:** `ai-governance-product-spec.md` §6, §7 (v0.2 cut).
**Companion:** `release-automation.md`.

This is the retention half of the product. v0.1 makes policy easy to *ship*; v0.2 makes usage *visible* and adds a live layer. Two coupled pieces: an **MCP server** (the live surface + a natural telemetry source) and a **dashboard** over the events it and the CLI emit.

Guiding constraints from the spec, non-negotiable:
- **Privacy-respecting by default.** Aggregate telemetry. **No prompt or code content collection in v1.** If we ever add content capture it is opt-in, per-org, and loudly disclosed.
- **Lightweight, self-hostable, boring, fast.** The free CLI must keep working with no server. Telemetry is additive, never required.
- **The control plane observes; it does not distribute.** Preserve the v0.1 property that no server can push rules into a repo. Telemetry ingest is one-way (client → server).

### Telemetry consent model (DECIDED)
Split by connection, which sidesteps the OSS-telemetry backlash entirely:
- **Unconnected OSS CLI: zero telemetry.** There is no control plane to phone home to, so nothing is collected. The pure open-source path is silent by construction — no "spyware" story to defend.
- **Connected / org-managed: opt-out, admin-controlled.** Once a repo/org connects to a control plane, telemetry is on by default and governed centrally by the org admin (enterprise norm). Disabling is a single documented config/env setting, disclosed on first connect, and never collects prompt/code content.

Rationale: enterprises expect admin-set opt-out; the OSS community punishes surprise opt-out. Making telemetry a property of *being connected* (a deliberate, paid/admin action) satisfies both. Document exactly what each event contains (see data model below) — transparency is the thing that keeps opt-out uncontroversial.

## Part A — MCP Server

### What it is
A server the SaaS ships (and can be self-hosted) that agents connect to as an MCP server. It gives the agent live, structured access to policy — and connecting *is itself* a telemetry event.

### Tools it exposes to the agent (candidate set)
- `check_policy(action)` — "am I allowed to open a port / use Lovable / add this model?" Returns allow / review-required / banned + the reason and the paved-path pointer. This is the catalog and rules from v0.1, made queryable instead of only static text.
- `paved_path(need)` — "where do I get an API key / a vault / the gateway here?" Returns the org's service catalog entry. Turns the agent into an ambassador for central services.
- `register_project(metadata)` — agent-initiated registration into the registry (the v0.3 self-service registry, pulled forward as an MCP entry point).
- `current_policy()` — the effective merged policy for this repo/org (what the static artifacts also contain), so an agent connecting fresh gets governance even before `esc sync` has run.

### Why it's worth it
- **Live queries** beat static text for decisions the agent makes mid-session ("is this port allowed?").
- **Telemetry falls out for free:** each connection identifies (org, team, repo, agent tool, model, session) with no separate collector — a big slice of Part B's data.
- **Static + live reinforce each other:** artifacts stay authoritative and offline-capable (determinism, air-gap); MCP adds the interactive layer.

### Auth model (DECIDED)
**Machine/agent → server: OAuth 2.1 device authorization grant with PKCE** — the pattern Claude Code and modern CLIs already use: open a browser if one is available, else print a URL + short code to paste. Familiar to our ICP, no passwords, works headless. The resulting token lands in MCP config, scoped **read-only + telemetry-only**.

**Human identity — self-hosted-first, built light, no third-party auth SaaS dependency.**
Routing a customer's identity through a hosted auth provider contradicts the product's self-hostable/air-gap positioning (institutions will reject it), so we own the identity layer. The core is small because we start OIDC-only and defer SAML (the one genuinely hard protocol):
- **Passkeys (WebAuthn)** via `go-webauthn` — the no-passwords default.
- **Verified email** for uniqueness + magic-link fallback.
- **OIDC relying-party** via `coreos/go-oidc` — "Sign in with Google / Azure AD / Okta" covers the bulk of enterprise SSO because modern IdPs are OIDC-capable. Same mechanism carries Google/Apple/social logins later.
- **No passwords, ever.**

**SAML: deferred, not built for v1.** When a specific enterprise mandates SAML/SCIM, two options that keep identity self-hostable — (a) add a Go SAML library (`crewjam/saml`) for that connection, or (b) front with a **self-hostable IdP**: **Zitadel** (Go-native, Apache-2.0, passkeys + OIDC + SAML + SCIM) is the lead candidate over Keycloak (Java) for a Go shop. The org runs its own identity plane; we don't reinvent SAML.

**WorkOS and similar hosted auth SaaS: explicitly NOT a dependency.** Only ever an optional managed convenience for *our* hosted tier if we want to skip SAML work — never required, never the self-host path.

Rejected: token-in-pack as the *primary* mechanism — it's tempting (dogfoods the format) but puts a credential in a committed file; keep it only as an optional CI/service-account path, never the interactive default.

### Hard design questions ❓
1. **Offline / degraded behavior.** MCP server unreachable → agent must fall back to static artifacts, never hard-fail. The static layer is the floor.
2. **Server-side vs artifact-side policy.** How much logic lives on the server (dynamic, per-request) vs in the rendered artifact (deterministic, auditable)? Lean: artifacts remain the source of truth; the server answers *from the same packs*, so answers are reproducible and auditable, not a second brain.
3. **Protocol churn.** MCP is evolving; A2A and others loom. Keep the tool surface small and version it.
4. **Multi-tenancy + self-host parity.** Same server binary runs SaaS-multi-tenant and single-org self-hosted.
5. **SAML/SCIM timing.** Core identity (OIDC + passkeys + email) is self-built and self-hostable. Open: when does the first SAML-only enterprise appear, and do we answer with `crewjam/saml` or a self-hostable Zitadel front? Decide when a real customer forces it, not before.

### Stack
Go, official Go MCP SDK (keeps CLI + server one codebase, one dep story). Reuse `internal/pack` + `internal/render` directly for policy answers.

## Part B — Telemetry & Dashboards

### Data sources (three, layered by richness and effort)
1. **CLI events (cheapest, ship first).** `esc sync`/`status`/`update` already know everything about *policy posture*: which packs at which versions, drift, constraint violations, when last synced. Add an opt-in `esc` reporter that POSTs a small event on these commands. This alone powers the "pack freshness / customization / drift-across-fleet" dashboards with zero new infrastructure on the client.
2. **MCP connection events (Part A).** Which agent tool, which model, which session, which org/team/repo — live.
3. **Provider admin APIs (richest for LLM usage).** Anthropic / OpenAI / Google admin/usage APIs for token consumption and cost, plus optional gateway (LiteLLM/Portkey) integration. This is where per-model token-by-day comes from at fidelity the client can't self-report.

### The metrics the user asked for → where each comes from

| Metric | Source | Notes |
|---|---|---|
| **Which users/teams use `esc`** | CLI events | Identity from token-in-config or git remote + author |
| **LLM usage by tool (filter by "Claude Code", Cursor, …)** | MCP events (tool self-identifies) + provider APIs | Tool attribution is easy from MCP; harder from provider APIs alone (see ❓) |
| **Token use per model, per day** | Provider admin APIs (primary), gateway (if present) | Time-series `(org, team, model, day) → input/output tokens, cost` |
| **Customized pack vs. defaults** | CLI events | Does the repo add team packs / local fragments beyond the org baseline? Emit a "customization fingerprint": # packs, whether any local-path/team pack present, whether managed block is the only governance content |
| **Last pack update / last server pull** | CLI + MCP events | `last_sync_at`, `last_update_at` per repo; `last_seen_at` per agent from MCP |

### Sort/filter dimensions (the dashboard's spine)
Every view should slice by: **org → department → team → repo/project**, **agent tool** (Claude Code / Cursor / Gemini CLI / other), **model** (provider + version), **time** (day/week/custom range), **pack** (name + version), and **status** (in-sync / drifted / constraint-violated). This mirrors the v0.1 data-model spine (Org → … → Repos → Policies → Events), so it composes cleanly.

### Dashboards (candidate set)

1. **Adoption & freshness**
   - Governed repos over time; % of known repos governed (the shadow-IT gap).
   - **Pack freshness histogram:** repos by "days since last sync"; flag repos on stale pack versions (a security signal — old packs = old rules).
   - **Customization split:** what fraction of repos run pure org defaults vs. add team/local customization. High customization can mean the defaults don't fit (product feedback) *or* teams are carving exceptions (governance signal).

2. **LLM usage & cost**
   - Token consumption per model, per day, stacked by team; cost attribution.
   - Filter by agent tool — e.g. "Claude Code token spend this week by team."
   - Model-vs-routing-policy: are teams using approved models for the right roles (fast for coding, reasoning for review)?

3. **Governance health**
   - Drift across the fleet: repos with modified/missing artifacts right now.
   - Constraint violations over time.
   - Turn-limit / escalation-rule trigger events (once the MCP server tracks sessions).
   - **Unsigned-source usage:** repos consuming `trust: unsigned` packs — a posture risk worth surfacing to a CISO.

4. **Anomaly & runaway (finance/security overlap)**
   - Token-spend anomaly detection per team/user (runaway-agent alerts — spec §3, §5).
   - Sudden new model/provider adoption (governance escalation trigger).

### Things worth adding that weren't on the list
- **Pack authorship & provenance view.** Who publishes the packs, are they signed, when last updated at the *source*. The supply-chain health of the policy itself — the thing an attacker would target.
- **Paved-path effectiveness.** Are agents actually querying `paved_path()` / following pointers? If a pack says "use the vault" and nobody adopts it, the policy isn't landing. Measures whether governance *works*, not just whether it's deployed.
- **Exception lifecycle** (ties to v0.3 review workflows): exceptions requested / granted / expired, and repos running on expired exceptions.
- **Project lifecycle / expiry** (the registry centerpiece): POCs past their TTL awaiting keep/kill/archive — the shadow-IT map leadership has never had.
- **"Ungoverned but active" detection.** Repos/agents showing LLM usage (provider APIs) with *no* `esc` presence. The highest-value list for a central IT buyer: where AI is happening with zero governance.
- **SIEM export of the same events** (spec: decided, ~v0.2). **Format DECIDED:** ship **syslog RFC 5424** + a **generic JSON webhook** first, with the JSON payload following the **OCSF** schema. Rationale: research shows **Caltech IMSS runs central syslog log servers and asks systems to ship logs there** ([IMSS lab/instrument security guidance](https://imss.caltech.edu/node/1369)) — syslog is the confirmed common denominator, no named-SIEM assumption required. OCSF (rather than legacy CEF) gives modern security-tool credibility for near-zero extra cost; add CEF only if a specific Splunk buyer demands it. **Demo sink:** a real free-tier target like **Axiom** or **Grafana Cloud** (simple JSON/syslog ingest, actual free plans) — avoid Splunk for demos (heavy, no meaningful free tier).
- **Per-user vs per-team identity resolution.** How granular before it's creepy? Default to team-level aggregation; user-level only where the org opts in. Privacy posture is a feature here.

### Telemetry data model (sketch)
Append-only event stream, one row per event, aggregated into rollups for the dashboard.

```
Event {
  ts, org_id, dept_id?, team_id?, repo_id?
  kind: sync | status | update | mcp_connect | policy_query | provider_usage | ...
  agent_tool?  (claude-code | cursor | gemini-cli | other)
  model?       (provider + version)
  packs?       [{name, version, source, signed, trust}]
  drift?       {in_sync, modified, missing, stale, constraint_violated}
  tokens?      {input, output, cost}   # provider_usage only, aggregate
  customization? {pack_count, has_team_pack, has_local_pack}
  session_id?  # correlate a run without capturing content
}
```
No prompts, no code, no file contents — ever, by default. Storage: boring append-only + periodic rollups (Postgres/timescale-shaped). Read-mostly, cheap, multi-tenant.

### Tool attribution from provider APIs (clarified constraint)
Provider admin/usage APIs (Anthropic/OpenAI/Google) report tokens per **API key / workspace / model / day** — **not per client tool.** An API key can be used by Claude Code, Cursor, or an arbitrary script; the provider cannot tell them apart. So "filter token spend by Claude Code" is reliable **only** where the tool self-identifies:
- **MCP connection events** — the agent tool identifies itself on connect (clean attribution).
- **Gateway integration** (LiteLLM/Portkey) — requests can be tagged per tool.
- **Separate API keys per tool** — an org convention we can *recommend* but not assume.

Product stance: **promise tool-level filtering where MCP/gateway data exists; show aggregate (key/workspace/model) otherwise**, and label which is which in the UI so a number is never silently mis-attributed.

### Open questions ❓
- **Client identity granularity.** Team-level aggregation by default; user-level only where the org opts in (SCIM from the SSO provider makes user identity available, but exposing it is a privacy choice).
- **Retention & residency.** Per-org retention windows; self-host for data-residency-constrained institutions (Caltech shape).
- **Gateway partnership depth.** How far to integrate with LiteLLM/Portkey for tool-attributed token data vs. relying on MCP events + provider APIs.

### Suggested build order
1. `esc` opt-in reporter → CLI-event ingest → adoption/freshness/customization dashboards (no MCP needed; fastest value).
2. MCP server (Part A) → connection telemetry → tool/model/session dashboards + live policy queries.
3. Provider admin API collectors → token/cost dashboards + anomaly alerts.
4. SIEM export.
5. Registry + exception/lifecycle views (bleeds into v0.3).

Each step ships a working dashboard slice and monetizes independently.
